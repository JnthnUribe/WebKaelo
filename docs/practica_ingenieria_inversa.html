1. Matriz de Problemas (Funcionalidades vs. Problemas Reales)

A continuación se presenta el mapeo entre las funcionalidades clave del sistema y los problemas específicos del mundo real que cada una resuelve:

Funcionalidad Implementada Problema del Mundo Real que Resuelve
1. Sistema de Rutas Geoespaciales con PostGIS
(Queries espaciales ST_DWithin, índices GIST, tipos GEOMETRY) 		Falta de Descubrimiento y Métricas de Proximidad.
Los ciclistas no pueden descubrir rutas ni servicios cercanos porque las aplicaciones deportivas convencionales (Strava, Komoot) carecen de un motor de búsqueda por proximidad geográfica integrado con datos de comercios locales. No existe una métrica de "distancia a servicio crítico" durante la actividad.
2. Row-Level Security (RLS) en todas las tablas
(Políticas de seguridad por rol y tenant isolation) 		Violación de Estándares de Privacidad de Datos.
Plataformas que manejan datos de ubicación y transacciones financieras sin aislamiento de datos por usuario violan estándares como ISO/IEC 27001 y GDPR. Los comercios exponen información sensible (ventas, inventario) si no hay control de acceso granular.
3. Arquitectura Modular por Features + TanStack Query
(Patrón feature-based, caché optimista, offline-first) 		Baja Mantenibilidad y Acoplamiento Excesivo.
Sistemas monolíticos dificultan la medición de cobertura de pruebas y el cálculo de métricas como MTTR (tiempo medio de reparación). El código fuertemente acoplado impide la evolución incremental requerida por estándares de calidad como ISO/IEC 25010.

2. Árbol del Problema — Técnica de los 5 Porqués

Problema Crítico Seleccionado: Violación de estándares de privacidad y control de acceso (Funcionalidad #2).

  1. ¿Por qué implementamos Row-Level Security en cada tabla?
    Porque sin ella, cualquier usuario autenticado podría acceder a datos de otros usuarios (órdenes, balances de wallet, ubicaciones).
  2. ¿Por qué sería posible ese acceso indebido?
    Porque la API REST auto-generada por Supabase/PostgREST expone todos los registros de una tabla por defecto, sin filtros de ownership.
  3. ¿Por qué las APIs exponen datos sin ownership?
    Porque el modelo BaaS (Backend-as-a-Service) prioriza la velocidad de desarrollo, delegando la seguridad a configuraciones explícitas del desarrollador.
  4. ¿Por qué eso representa un riesgo medible?
    Porque existen métricas de compliance (ej. OWASP Top 10, ISO 27001) que clasifican "Broken Access Control" como vulnerabilidad crítica, resultando en sanciones legales y pérdida de confianza.
  5. ¿Por qué es relevante para métricas de software?
    CAUSA RAÍZ: Porque el cumplimiento de estándares de seguridad (como RLS) es una métrica de calidad no funcional que impacta directamente atributos medibles como Seguridad y Conformidad definidos en ISO/IEC 25010.

Planteamiento del Problema (sin mencionar la solución)

En el desarrollo de aplicaciones serverless que manejan datos de ubicación, transacciones financieras e información personal, existe un riesgo latente de exposición de información sensible cuando no se implementan políticas de control de acceso a nivel de registro. Este problema se amplifica en arquitecturas BaaS donde las APIs se generan automáticamente. La ausencia de mecanismos de aislamiento de datos entre tenants (usuarios/comercios) constituye una violación directa de estándares internacionales de seguridad de la información, exponiendo a la organización a vulnerabilidades clasificadas como críticas por OWASP y comprometiendo atributos de calidad definidos en normas ISO/IEC para ingeniería de software.

3. Alineación Metodológica (Pregunta, Objetivo e Hipótesis)

3.1 Pregunta de Investigación

¿De qué manera la implementación de estándares de seguridad (RLS) y arquitectura modular influye en los atributos de calidad medibles (seguridad, mantenibilidad, portabilidad) de una plataforma móvil serverless en el contexto del cicloturismo regional?

3.2 Objetivo General

Desarrollar una plataforma móvil que integre estándares de seguridad a nivel de datos (Row-Level Security) y patrones arquitectónicos modulares (feature-based), para garantizar el cumplimiento de métricas de calidad no funcionales (ISO/IEC 25010) en un sistema de comercio geolocalizado, permitiendo la medición objetiva de atributos como confidencialidad, modularidad y tolerancia a fallos.

3.3 Hipótesis de Solución

"Si se implementa un sistema móvil con políticas Row-Level Security en PostgreSQL y arquitectura feature-based con caché optimista, entonces se logrará un 100% de cobertura en políticas de acceso y una reducción del acoplamiento entre módulos (medible por fan-out/fan-in), debido a que estas prácticas son estándares reconocidos por ISO/IEC 25010 para garantizar los atributos de Seguridad y Mantenibilidad en sistemas de software."

4. Justificación Teórica (Fundamentación con Citas)

4.1 Conceptos Teóricos Clave

  1. Atributos de Calidad del Software (ISO/IEC 25010) — Modelo de calidad que define características como Seguridad, Mantenibilidad y Portabilidad.
  2. Row-Level Security (RLS) — Mecanismo de control de acceso a nivel de fila en bases de datos relacionales para garantizar aislamiento de datos.

4.2 Mini-Fundamentación Teórica

El proyecto KAELO no adopta tecnologías arbitrariamente, sino que fundamenta sus decisiones en estándares internacionales de ingeniería de software. La arquitectura implementada responde directamente a las características de calidad definidas en la norma ISO/IEC 25010:2011, la cual establece un modelo de calidad del producto software con ocho características principales, incluyendo Seguridad y Mantenibilidad (ISO/IEC, 2011).

Específicamente, la implementación de Row-Level Security (RLS) en PostgreSQL atiende la sub-característica de Confidencialidad, garantizando que "los datos solo sean accesibles por aquellos autorizados" según el estándar. Por otro lado, la adopción de una arquitectura modular por features responde a la característica de Modularidad, que la norma define como "el grado en que un sistema está compuesto por componentes discretos de manera que un cambio en uno tenga mínimo impacto en otros".

Adicionalmente, según Bass, Clements y Kazman (2012) en su obra seminal sobre arquitectura de software, "la modularidad es la táctica arquitectónica principal para lograr mantenibilidad, y las decisiones de seguridad deben ser explícitas en la arquitectura, no agregadas después". Esta afirmación valida la decisión de integrar RLS desde el diseño inicial del esquema de base de datos y no como un parche posterior.
